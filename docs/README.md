# midigpt — browser demo

A piano transformer (trained on MAESTRO) running entirely client-side:
onnxruntime-web generates event tokens autoregressively, and Tone.js plays them
through a real sampled grand piano. Pick a composer, hit Generate.

Part of the single `midigpt` repo (training code lives in the parent). This is
the `docs/` folder so **GitHub Pages** can serve it (Settings → Pages → Deploy
from a branch → `main` / `/docs`). The `model.onnx` is generated by the parent's
`export_onnx.py` and hosted on Hugging Face (`gmmeyer/midigpt`); everything else
here deploys as the static page.

**Currently shipping run0** — the 27M model, exported fp32 — chosen over the
larger composer-conditioned model because it sounded cleaner. Trade-off: the
composer dropdown primes with a composer token but run0 wasn't trained to steer
on it, so its effect is weak. (The conditioned 41M model does steer; re-export
that checkpoint to swap it in.)

## Run locally

A static server is enough (opening `index.html` via `file://` won't work — the
`.wasm` and `.onnx` fetches need HTTP). From the repo root:

```
python -m http.server 8177 --directory docs
# open http://localhost:8177
```

## Files

- `index.html` / `app.js` — the UI and the generation/decode/playback loop.
  The decoder mirrors the training project's `tokenizer.py` exactly
  (byte-for-byte verified). Playback uses Tone.js's Salamander grand-piano
  samples (loaded from a CDN on first Play, with a synth fallback if offline) —
  a raw synth makes dense piano writing sound harsh, sampled piano doesn't.
- `model.onnx` — MusicGPT exported fp32 (~106 MB; loads instantly from
  localhost). **Gitignored** (a build artifact, and too big for GitHub's 100 MB
  limit) — regenerate it before running, or host it externally for deploy.
  Regenerate from a checkpoint:
  `uv run --with onnx --with onnxruntime python -m midigpt.export_onnx \
   --checkpoint <ckpt>.pt`  (add `--quantize` for a ~4x-smaller int8 build,
  but int8 noticeably alters output — prefer fp32/fp16 for quality).
- `config.json` — vocab layout + composer→id map the JS side reads.

## Backend

Tries WebGPU first (with a warmup inference), falls back to WASM if the warmup
throws. fp32 runs fine on both.

**Speed:** generation is **cacheless** (each token re-runs the whole context),
so it's ~3–5 tokens/sec on WebGPU — the length dropdown is labelled with rough
waits. The right fix is a **KV-cache** (export the model with past-key/value
inputs and reuse them per step); that would make it near-instant per token and
is the main open optimization. `web_context_cap` (in `config.json`) bounds the
per-step cost by capping how much history each step attends to.

EOS is suppressed during sampling: the model emits it early ~10–20% of the time,
which would truncate a piece to a stub, so the demo generates the full requested
length and keeps improvising.

## Deploy (Hugging Face + static host)

`model.onnx` is too big for GitHub, so it lives on Hugging Face
(`gmmeyer/midigpt`); the rest of `docs/` deploys via GitHub Pages.
`config.json` ships in the repo next to the page, so only the model needs
uploading. HF serves with permissive CORS, so the cross-origin fetch just works.

1. Upload the model to HF (only the model — config stays in the repo):
   `huggingface-cli upload gmmeyer/midigpt docs/model.onnx model.onnx`
2. `app.js` already points `HF_URL` at `gmmeyer/midigpt`; it uses `./model.onnx`
   on localhost and HF everywhere else, so local dev and deploy both work.
3. In the repo's GitHub settings, enable Pages → Deploy from a branch →
   `main` / `/docs`. The demo lands at `gmmeyer.github.io/midigpt/`.

**Download weight:** the deployed model is what users download once. fp32 run0
is ~106 MB — fine but heavy over the network. int8 (`--quantize`, ~27 MB) is
much lighter but noticeably alters output; fp16 (~54 MB) would be the sweet spot
but the export path needs fixing first (the fp32→fp16 converter chokes on the
export-only attention/norm ops).
